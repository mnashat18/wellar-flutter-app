# Wellar source audit — working report

Audit date: 2026-09-24. This document is being assembled in user-journey order. Only the coverage explicitly listed below has been reviewed. An issue described as a source defect is supported by an inspected implementation; layout/device behavior requiring execution is identified separately. Production backend configuration is not inferred from old documentation or sanitized exports. No application fixes are part of this audit.

## 1. Authentication journey

### Actual routes and task steps

`main.dart:45` restores secure storage before `runApp`; `main.dart:318` installs `SplashScreen` as home. A logged-out splash goes directly to `PublicEntryScreen` (`splash_screen.dart:148–152`). It does not display the older onboarding screen.

* Email login: public entry → Sign in → email/password → Sign in → splash validation → workspace resolver → role shell or workspace-access screen. Two user-selected route/submit actions plus two inputs, before any workspace recovery.
* New company account: public entry → Start organization → first name, last name, email, password, confirmation, legal checkbox → Create account. If registration returns a session, splash follows. Otherwise Login opens with the email filled, and another password entry/login is required. Company setup follows separately; account creation does not itself create a company.
* Forgot password: login → Forgot password → email → Send reset link → email application/browser reset page → Back to sign in. The mobile implementation requests a reset link; it neither accepts an OTP nor sets a replacement password.
* Invitation: public entry → invite-code sheet → Continue → invite lookup → account creation/sign-in for logged-out users, or Continue/claim for logged-in users. A successful direct claim opens a forced-completion scan.
* `OnboardingScreen`, `MobileAuthScreen`, and `AuthWelcomeScreen` have no production constructor callers in `lib/`. `VerificationScreen` is called only from `MobileAuthScreen`. `AuthIntentScreen` is called from the older `PublicHomeScreen`; its reachability must be considered with that screen. These distinctions prevent treating dormant OTP UI as a proven production authentication bypass.

### A01 — High: Arabic selection is forcibly replaced with English

Evidence: `lib/state/app_language_state.dart:14–16,35–46,58–64`; `lib/main.dart:171–173,267–275`.

`fromCode` always returns English, saved Arabic is overwritten, and `setLanguage` ignores its argument. Declaring Arabic in `supportedLocales` does not make it available through this controller. This corrects the previous audit's statement that Arabic/RTL support was functional. All screens inherit this problem.

Fix: map `ar` to `AppLanguage.arabic`, persist the requested language, preserve supported stored values, and then test `Directionality` and translated strings throughout the app. Do not mark RTL complete until the physical left/right alignments and English literals below are repaired.

### Splash and pre-frame initialization

Observed states: no session routes immediately to public entry; existing session calls `/users/me`, then resolves workspace; each awaited stage has its own eight-second timeout. Timeouts show Retry and Use another account/Go to login. The slow-state labels rotate on a timer rather than representing actual backend stages. Ambient animation checks `MediaQuery.disableAnimations`; intro and transition animations still run. There are no form fields or permission prompts on this screen itself.

**A02 — High: secure-storage failure can prevent the Flutter UI from starting.** `lib/main.dart:45–48` awaits `Session.init()` before `runApp`; `lib/state/session.dart:28–36` performs seven reads with no error recovery. The later `ErrorWidget.builder` cannot render an initialization failure before `runApp`. Fix: start an initialization gate that catches storage exceptions, shows retry/re-authentication, and treats inconsistent credentials as an invalid session. Test failed reads and restored/corrupt key storage; do not silently wipe storage for a transient failure.

**A03 — Medium: some splash errors leave the loading screen indefinitely.** `lib/screens/splash_screen.dart:297–302` only logs generic errors; unlike the timeout branch, it never sets `_startupFailed`. Fix: use one terminal error-state function in every failed branch and retain a usable Retry action. Inject unexpected resolver and plugin errors in a widget test.

**A04 — High: timeout/retry does not cancel the previous session/workspace operation.** `splash_screen.dart:155–177,615`; `auth_service.dart:406–423` writes profile state after a network response; `session.dart:39–81` has no session-generation check. A timed-out operation can continue after retry or an account change, and mutate shared session state. Fix: attach a session generation to every auth operation, cancel old Dio requests, and reject state writes when the generation/token changed. An eight-second `Future.timeout` is not a cancellation primitive ([Dart documentation](https://api.dart.dev/dart-async/Future/timeout.html)).

**A05 — Medium: account-switch escape retains the old session.** `splash_screen.dart:638–643` clears workspace context and opens Login without clearing access/refresh tokens or identity. The same pattern exists in `workspace_access_screen.dart:363–368,401–406`. Fix: route through an atomic account-change operation that captures old revocation credentials, clears local identity and auth headers, invalidates user-scoped caches, and only then opens Login. See A19 for the existing logout race.

**A06 — Medium: splash is not height-adaptive; text is not localized.** `splash_screen.dart:328–340` uses a non-scrollable Column with an Expanded brand area and bottom panels; `:26–30,393–417,589–599,625,655` contain English literals. Large text/landscape can exceed available vertical space; this is a layout risk pending a widget/device test, not a claimed screenshot finding. Fix: localize status/error/action copy and use a scrollable recovery layout that accommodates large text. Keep the existing reduced-motion ambient behavior and extend it to intro/transitions.

### Public entry and invite-code bottom sheet

All three entry actions are wired: Sign in pushes Login; Start organization pushes Register; Have an invite code opens the sheet. Blank code produces an inline error. Nonempty input closes the sheet and opens Invite. The public page itself needs no domain API, so network loss does not block rendering its static content. Fonts are requested through GoogleFonts and are not bundled in `pubspec.yaml`; first-install font behavior needs a network-disabled test.

**A07 — Low: invite-sheet controller is never disposed.** `lib/screens/public_entry_screen.dart:22–39` allocates a controller outside the sheet; neither owner disposes it. Fix: let the sheet state own/dispose the controller, or await the sheet and dispose in `finally`.

**A08 — Medium: invite-sheet validation and layout are incomplete.** `public_entry_screen.dart:338–345` accepts any nonempty length; `:351–362` contains a non-scrollable Column above the keyboard; `:390–393` requests capitalized input for a potentially case-sensitive token. Fix: apply the server's actual token format/length contract, disable unintended capitalization/autocorrection, support pasting the canonical invitation URL safely, and place the sheet content in a constrained scroll view. Keyboard/landscape overflow needs execution. This is not evidence of SQL injection: the token is a Dio query-parameter value, not concatenated SQL.

**A09 — Medium: entry typography/colors and action roles diverge from shared components.** `public_entry_screen.dart:99–120,123–135,241–278` uses Space Grotesk/Inter, blue gradient InkWell buttons and different card tokens; register/login use gold buttons; `WellarTheme.primary` is teal. The public primary InkWell has text/tap semantics but does not explicitly advertise a button role. Fix: implement these variants in the common design system and use a native button or explicit `Semantics(button: true)`; localize all entry/sheet text and use directional alignment at `:190`. Do not equate a lack of explicit Semantics wrappers with a lack of semantics on every Material widget.

### Older onboarding, auth intent, and welcome screens

`OnboardingScreen` provides Google, Login, Create Account and View plans. Its Google action has a loading guard and maps auth failures to an overlay; the other navigation controls remain active while Google is pending. The error overlay dismisses on tap anywhere. `AuthIntentScreen` provides create/join/sign-in; joining without a stored token opens `WorkspaceAccessScreen`, whose authentication guard redirects a logged-out user to Login. `AuthWelcomeScreen` defaults to auto-navigation after 900 ms and has a Continue button with a duplicate-navigation guard. All three are static apart from the Google operation and downstream routes.

**A10 — Low, dormant flow: onboarding promises “Google sign-in only” beside email-login/register actions.** `lib/screens/onboarding_screen.dart:210–246`. Fix the copy if this screen is retained; otherwise remove its obsolete entry flow. Its hardcoded headline and marketing text also need localization. The error overlay at `:277–308` needs dialog semantics, focus containment and an explicit dismiss control if made reachable.

**A11 — Low, dormant flow: welcome auto-advances before users can read account/workspace facts.** `lib/screens/auth_welcome_screen.dart:27,39–42,118–151`. Fix: require explicit Continue or provide an accessible opt-out; localize the fact labels. No production caller was found, so this is not asserted as a current user-facing blocker.

### Registration

Actual checks: trimmed nonempty first and last names; `^[^@\s]+@[^@\s]+\.[^@\s]+$` email; password length 10–128 with one ASCII letter and a digit; exact nonempty password confirmation; legal checkbox. Invalid fields are marked on blur or submit and show inline errors; `_error` is a top-of-form notice. Valid submission disables the primary action and calls `POST /users/register`. Offline failure retains the controllers while the screen remains mounted. No durable draft exists; leaving the route loses the form. No password is written to Session storage.

**A12 — High: registration validity does not update as fields are edited.** `lib/screens/register_screen.dart:236–255,556–558,685` calculates `canSubmit` in the parent but the shared field's `onChanged` is empty. It only re-evaluates on other events such as blur, checkbox/visibility taps, or rebuilds. Example: accept the checkbox first, type the final valid confirmation while keeping focus, and the previously disabled action can stay disabled. Correcting an invalid value also leaves stale field messages. Fix: pass an `onChanged` callback that rebuilds/clears stale server feedback, or listen to controllers with a form/value-listenable model. Test typing the final character without changing focus.

**A13 — Medium: auth fields are missing password-manager/autofill and explicit visibility labels.** `register_screen.dart:447–485,677–689`; `login_screen.dart:281–291,395–408`. Password toggles have neither tooltip nor descriptive state; fields use external labels/hints but no autofill groups/hints; password input uses default autocorrection/suggestions. Fix: use `AutofillGroup`, appropriate `AutofillHints`, persistent input labels, password-specific keyboard settings, and localized Show/Hide password tooltips. Confirm screen-reader announcements with a semantics test/device.

**A14 — Medium: auth errors and large parts of the form bypass localization.** `register_screen.dart:128–147,173–224,304–325,368–413,456–489,501–544,549–555`; `login_screen.dart:92–96,199–213,258–278,319–359,442–486`; `forgot_password_screen.dart:59,73–79,107–120,139–156,178–183,221–246`. Fix: move literals into translation keys with placeholders and structured auth-error codes. Do not use substring searches over server messages as the primary classification API. For RTL, replace `Alignment.centerLeft` with `AlignmentDirectional.centerStart`, and preserve LTR direction explicitly for email/token values where needed.

**A15 — Low: registration input and navigation details are inconsistent.** `register_screen.dart:125–130` has no name maximum; `:442–445` submits from the first password field before confirmation rather than moving focus; `:277–292` labels its icon as Home but replaces the page with Login; `:509,527` ignores URL-launch failure. Fix: apply server-compatible name/email bounds without excluding valid Unicode names, use Next from password to confirmation, give the back control an accurate label/destination, and await/check legal-link launch results. Client validation is usability, not a backend injection defense; no SQL/HTML execution was found in these fields.

**A16 — Medium: auth keyboard padding is applied twice.** `login_screen.dart:158–172` and `register_screen.dart:256–270` leave Scaffold's default keyboard resize enabled while additionally padding by `viewInsets.bottom`. Their min-height constraint also ignores scroll-view padding. Fix: use one keyboard-inset strategy and calculate the child's minimum height after padding, or use a sliver fill layout. Validate 320×568, landscape and 200% text; exact overflow is not asserted without execution.

### Login, Google exchange, and shared request behavior

Login trims email, checks its basic format, and requires a nonempty password. It deliberately does not impose signup password complexity on existing credentials. Validation/network errors retain the input. Sign in and Google disable while pending; Forgot password, Back and Create account remain available. `_loadMe` and invite claiming execute after token receipt and are swallowed on error; splash later validates the session again. The configured Google endpoint is a separate HTTPS origin and receives `id_token` plus optional `access_token`.

**A17 — High: auth headers survive skip-auth requests and logout.** `lib/services/directus_client.dart:21–28` only skips adding headers; it does not remove an inherited default header. `:267–272` sets a persistent default Authorization after refresh. `:190–195` adds Authorization on every retry regardless of `skip_auth`. `auth_service.dart:289–298` uses the same client to POST to another origin with `skip_auth`. Thus an existing Directus credential can be sent to the exchange origin, and a default credential can remain after Session.clear. Fix: never store user auth in Dio defaults; always remove an inherited Authorization header first, add it only for explicitly authorized origins and requests, and preserve this rule on retries. Clear defaults synchronously on logout. Test both first attempt and network retry after a refresh and after session clear.

**A18 — High: automatic transport retries replay non-idempotent operations.** `directus_client.dart:51–94,145–158,199–210` retries connection/send/receive failures without checking HTTP method or idempotency. Auth registration, reset-mail requests, invite PATCHes, and other app writes use this client. A server may commit before the response disappears; automatic replay is therefore not proof-safe. Fix: retry safe reads by default, require server-enforced idempotency keys for creates/actions, and use replayable request-body factories for multipart operations. Report ambiguous success and reconcile before allowing manual resubmission.

**A19 — High: logout races with the next login and late requests.** `lib/screens/profile_screen.dart:399–422` navigates to Login and starts `AuthService.logout()` unawaited. `auth_service.dart:455–479` awaits unregister, server logout, Google/Firebase sign-out before clearing Session. During that window old credentials remain available; signing in again can install new credentials that the old logout subsequently clears. `_loadMe` can also write an old identity with whichever token is currently stored (`:416–423`). Fix: capture old credentials, immediately invalidate a session generation and local state/header/caches, then perform bounded best-effort revocation against the captured old credentials. Block old in-flight writes from committing. Do not let cleanup read or erase the next session.

**A20 — Medium: refresh failure has no central terminal session-expired transition.** `directus_client.dart:31–97,291–305,333–335` ultimately forwards the failed request; it does not invalidate credentials or route the app. Only `AuthService.validateSession` clears on a final 401 (`auth_service.dart:439–446`); 403 becomes validationUnavailable. Fix: distinguish invalid/revoked refresh from offline/5xx failure; emit a global expired-session state only for definite auth failure, clear protected views, and preserve unsent nonsecret form state for re-authentication. Keep 403 as authorization failure rather than automatic logout.

**A21 — Medium: user email and ID are logged in release builds.** `auth_service.dart:423` directly prints both with no debug guard. `main.dart:34–41` prints arbitrary exception strings and stacks. `auth_service.dart:381–397` sanitizes only top-level token/secret keys and logs nested/string exchange errors under debug at `:305–307,326–328`. Fix: remove PII output, redact recursively by an allowlist of permitted fields and types, and avoid logging raw network bodies. Even debug builds must not log credentials. Local Flutter SDK `packages/flutter/lib/src/foundation/print.dart:37` explicitly states that `debugPrint` also logs in release. Token-presence booleans are not themselves leaked raw tokens; the prior report blurred that distinction.

**A22 — Medium, deployment contract: supplied Google endpoint and mobile request disagree.** `auth_service.dart:294` sends `id_token`; `backend/directus-extension-endpoint-google-mobile-exchange/src/index.ts:375–381` reads `idToken`. The second packaged implementation `backend/google-mobile-exchange/dist/index.js` reads the same camel-case key. The mobile URL is `/auth/google/mobile-exchange` on a separate service, so these files alone do not prove the live endpoint fails. Fix: identify the deployed handler, standardize the path/body contract and add a contract test using the actual mobile payload. The supplied extension verifies Google audience and email verification (`src/index.ts:101–114,384–404`), but its user query excludes account status and its session construction uses version-dependent internal methods (`:143–150,198–246`); test suspended users, MFA requirements, actual expiry, revocation and the installed Directus version before claiming those controls are enforced.

### Forgot password

`POST /auth/password/request` supplies email and `${publicWebBaseUrl}/reset-password` with skip-auth/skip-refresh flags (`auth_service.dart:132–174`). Successful 2xx displays an account-enumeration-safe message and instructions to finish in the browser. All other outcomes become unavailable. This app has no reset-token creation/verification/new-password endpoint implementation; entropy, expiry, single-use, rate limiting and web-page validation require the reset backend/web source or a controlled test.

**A23 — Medium: keyboard/large-text recovery screen cannot scroll.** `lib/screens/forgot_password_screen.dart:90–95` wraps the whole screen in a fixed Column; errors and the software keyboard add height. Fix: use a scroll view within SafeArea, test error and success states with large text, and keep primary/back actions reachable.

**A24 — Medium: Back duplicates Login rather than returning to it.** `forgot_password_screen.dart:100–105,155–163,229–237` uses `pushReplacement(LoginScreen)` even though Login pushed ForgotPassword. The previous Login remains underneath and invite constructor state is lost in the new instance. Fix: pop with the edited email as a result, and update the original Login; retain invite context centrally. Native/system back and on-screen Back should behave consistently.

**A25 — Low: reset errors do not distinguish recoverable causes.** `auth_service.dart:154–174` collapses 429, 403, network failure and unavailable endpoint into the same result; `forgot_password_screen.dart:73–79` gives one message. Fix: map rate limit to a retry-after state and connectivity to a connection/retry state, while keeping success wording neutral about account existence. Reset retransmission is also affected by A18.

### Mobile/OTP legacy screens

Phone submission checks only nonempty input; email submission checks nonempty and `contains('@')`. Both immediately navigate to Verification. No send API is called. Verification accepts any six-character assembled input and routes to `RoleShellRouter` or Login. Its 90-second timer only controls the resend UI; resend restarts the timer and claims success without an API. The role router subsequently validates the session, so this is not evidence that an unauthenticated user obtains server data. No production caller of MobileAuthScreen was found.

**A26 — Medium, dormant functionality: OTP UI falsely claims sending/verification.** `lib/screens/mobile_auth_screen.dart:30–66`; `lib/screens/verification_screen.dart:68–98,167,178–182`. Fix: remove/feature-disable these screens until a real challenge service exists, or implement server-generated cryptographically random challenges bound to destination/session, server expiry, attempt limits, resend limits, and session issuance only on successful verification. Never promote the length check to an authentication decision. No OTP secret, generator or real expiry enforcement exists here to audit.

**A27 — Medium, dormant component: OTP input is fixed-width, accepts nondigits, and has incompatible paste handling.** `lib/widgets/otp_input.dart:47–64,71–82` uses six 44-wide fields (264 logical pixels before surrounding padding), no digits-only formatter and `maxLength: 1` despite attempting multi-character paste distribution. Verification adds 40 screen-padding pixels plus 36 card-padding pixels, leaving 244 at a 320-wide viewport, less than the 264 required. Fix: use a single logical one-time-code field with autofill and digit filtering rendered into adaptive cells; preserve LTR code order in RTL; support paste/backspace and accessible position labels. Execution should confirm the default max-length formatter's paste behavior on each platform.

### Invitation details and claim

Lookup uses GET `/items/request_invites` with the token as a query parameter and a series of field-schema fallbacks. It requests email/phone/requester/company details. The UI shows a skeleton then a card or invalid-invite card. Logged-out users can proceed to signup/login; logged-in users can claim. Claimed/expired status leads to Back to Home. Server scope must control which details are readable; a client token filter alone is not access control.

**A28 — Medium: offline/403 invite lookup is shown as an invalid or expired invitation.** `lib/screens/invite_screen.dart:54–65` never checks `snapshot.hasError`, so any lookup exception becomes the same null-data invalid message. There is no retry for the lookup. Fix: separate transport/permission failure from a successful not-found response and expose retry retaining the code.

**A29 — High: invitation claim is non-atomic and does not enforce time/recipient in client path.** `lib/services/invite_service.dart:61–117,183–208` reads status then PATCHes the invite to claimed before PATCHing the request's recipient. Connection loss or rejection of the second PATCH leaves a consumed invitation without the assignment, and a second claimant can race the read/update. The read for claim omits `expires_at`; `lib/models/invite_details.dart:30–32` only considers a status string, not elapsed expiry or cancelled/revoked states. The claim method does not compare invite email to the authenticated user. These are confirmed client-path omissions; an exploitable authorization bypass depends on server policy and is not asserted. Fix: replace both PATCHes with a protected transactional claim endpoint that derives user ID from authentication, validates recipient, allowed status and server time, consumes once and assigns atomically. Return typed already-claimed/wrong-account/expired results; use an explicit actionable-state allowlist in UI.

**A30 — Medium: a failed/no-op claim can silently discard the pending invitation.** `auth_service.dart:67–70,239–242`; `invite_screen.dart:272–291` clear pending state even when `claimInviteByToken` returns null. Fix: clear only after a confirmed successful claim or a user-visible terminal invalid/expired decision; return a result enum instead of nullable success and preserve retriable errors.

### Workspace access and role-shell boundary

No active membership gives a company-create screen with an invite field and Use another account. The error mode gives only Retry and Use another account. Retry can open a membership chooser and call workspace-session sync. Employee/manager/HR/owner are the four recognized mobile shells (`role_based_shells.dart:32,73–80`); an independent `admin` shell does not exist. The `AdminScanRequestsScreen` name does not mean there is a fifth mobile role.

**A31 — Medium: workspace failure detail/state is discarded by the view.** `workspace_access_screen.dart:106–125,194–200` stores session-expired/forbidden/other messages, but `:375–409` always shows a connection warning and ignores `_statusMessage`. A nonactivated account therefore receives connectivity advice. Fix: render distinct session-expired, pending activation, restricted, no-membership and transport-error states, with corresponding sign-in/contact-admin/retry actions. Catch unexpected failures in `_refreshMembership` as well as OrganizationServiceException.

**A32 — Medium: workspace forms/chooser lack scrolling and empty invite feedback.** `workspace_access_screen.dart:281–287,297,342–357,428–477` uses fixed Columns and renders every membership at once; blank Join simply returns. Fix: use scrollable page and bounded ListView sheet, display an inline required-code error, and disable duplicate submissions. Keyboard and many-membership cases need execution.

### Deep links affecting auth

**A33 — Medium: invite URI parser accepts HTTP, arbitrary HTTPS hosts and loose path placement.** `lib/main.dart:381–396` accepts an `invite` segment anywhere, with no HTTPS host allowlist or token format/length validation. Android declares both HTTP and HTTPS invite filters without `autoVerify` (`android/app/src/main/AndroidManifest.xml:56–67`) and a generic custom `app` scheme. These facts do not prove arbitrary URLs can bypass the OS filter or backend authorization. Fix: exact allowlisted HTTPS origin/path, no userinfo/unexpected port, explicit token contract, verified Android links and matching iOS associated domains. Use a protected server claim endpoint as in A29.

**A34 — Medium: cold-start links can be consumed before navigation is ready and repeated links are permanently suppressed.** `main.dart:365–376` sets `_lastInviteToken` before checking navigator context; if context is null it returns without scheduling a later delivery. The same token is then ignored for the lifetime of the listener even after failure/back/logout. Fix: queue intents until startup/auth routing completes; deduplicate only in-flight delivery, reset on terminal outcome, and retain the original destination through authentication.

**A35 — Medium: iOS invite-link registration is missing from inspected platform source.** `ios/Runner/Info.plist:52–62` contains only the Google reversed-client-ID scheme; no iOS entitlements file was found by repository file search. Fix: configure associated domains/host association and the intended custom invite scheme if retained, then verify signed cold/warm starts. This is source configuration evidence, not a claim about an externally modified archive.

### Profile/session exit encountered during auth tracing

Profile falls back to securely stored identity if live profile loading fails (`profile_screen.dart:381–396`) and shows a partial-info warning. It has no editable profile form. Logout confirmation has Cancel/Sign out; deletion confirmation opens an HTTPS external page with launch failure feedback and never itself calls a deletion API. Switch organization only appears for more than one supported organization and opens an informational web-switch dialog.

**A36 — Medium: account status is asserted Active even when unavailable.** `profile_screen.dart:193,222` supplies fixed/default active labels independent of a successful status fetch. Fix: render verified backend status or Unknown/Unavailable with last-verified information; do not present stale permission/status as fresh.

**A37 — Medium: Switch organization is a dead-end instruction rather than a switch/link.** `profile_screen.dart:333–338,581–605` displays a dialog instructing users to switch on the web but provides only Got it. Fix: either reuse the existing membership picker/session-sync flow or label the action Open web settings and provide an HTTPS link plus a refresh action on return. Offline/error while fetching switchable organizations hides the control entirely (`:310–318`); show a retryable state instead.

## 2. Organization creation, switching and invitations

### Canonical workspace context and switching

The active production resolver calls `GET /wellar/workspaces/context` and accepts an active membership only when it has a matching current user, nonempty membership and business IDs, and active/accepted status (`organization_service.dart:408–539`). `WorkspaceAccessScreen` presents a membership choice before calling `POST /wellar/workspaces/switch`. The older `resolveActiveWorkspace()` still selects the first active row, but repository search found no production caller of that method. It is dormant code, not evidence that login currently auto-selects the first membership.

**A38 — High: a successful switch can be reported as a failure.** `organization_service.dart:604–675,901–913,1034–1090` receives a successful switch response, then requires replacement credentials from that response and later requires fresh `/users/me` and canonical context checks. `_applySwitchSessionCredentials` returns false if the switch payload has no `access_token` (`:2680–2718`); the service then clears local context and throws although the server-side switch may have committed. The subsequent role/context checks can also throw after commit. The existing switch test at `test/organization_switch_flow_test.dart:129–245` expects a successful payload with empty `data` to be followed by `/auth/refresh`, but the inspected implementation does not do that, so the test and implementation disagree. Fix: define and test the switch endpoint response contract; treat a confirmed switch response as the mutation result, install returned credentials when present, and represent context refresh failure as a separate recovery state. Do not clear a valid session or invite a second switch solely because a follow-up read failed.

**A39 — Medium: the primary business-profile helper can select a non-active organization.** When canonical context is absent, `organization_service.dart:1496–1549` calls `_fetchBusinessProfileFromMembership`, which requests a single membership without ordering and eventually retries without an active-status filter (`:1898–1925`). The helper returns that profile as the "primary" business; callers include reports, activity, subscriptions and business-center services. Server authorization still governs the data, so this is a workspace-context/data-selection defect, not a proven cross-tenant read. Fix: require a verified active canonical context for workspace-scoped operations and expose a distinct no-active-workspace result. Remove the arbitrary-membership fallback from this helper.

**A40 — Medium: organization diagnostics can emit personal or backend response data.** The dormant legacy resolver logs current email, its membership query and full response body (`organization_service.dart:1131–1178`), while the production `_loadCurrentUser` error branch logs `/users/me` response data (`:1468–1475`). The create screen logs failed response bodies (`business_profile_wizard_screen.dart:574–579`). Fix: log an operation name, status and non-sensitive error code only; redact personal details and server payloads in release and debug builds.

### Create workspace

The three-step wizard validates visible fields, then calls `POST /wellar/workspaces/create` with a generated idempotency key. A 2xx response is followed by token refresh and up to two canonical-context reads before the owner shell opens. The screen reports creation separately from activation when those reads fail.

**A41 — High: retries use a new idempotency key after an uncertain create result.** `business_profile_wizard_screen.dart:473–512,647–649` generates a time-based key for every `_submit` call. If the server creates the workspace but the response is lost, the visible retry sends a different key; the service only coalesces simultaneous calls with the *same* key (`workspace_creation_service.dart:26–58`). This defeats the purpose of the key across retries and can create duplicate workspaces unless the server applies an independent uniqueness rule. Fix: create a random key once per intended workspace, retain it across ambiguous failures and app recovery, and rotate it only after a confirmed terminal outcome or an intentional new workspace. Verify server deduplication behavior.

**A42 — Medium: successful creation is coupled to token refresh.** `business_profile_wizard_screen.dart:530–546` stops after a failed `/auth/refresh` even when create returned 2xx; the wizard remains available to retry, which compounds A41. Fix: use the create response and canonical context as the source of creation status; handle refresh as recoverable session work and offer a refresh-access action without reissuing create.

### In-app organization invitations

The in-app list queries `request_invites` by the authenticated user's email and filters pending states again in memory (`organization_invitation_service.dart:39–88`). Acceptance and decline check the email locally, then PATCH an invitation. A successful acceptance polls canonical context and may switch back to the previous membership if the server moved the active workspace. Whether server-side permissions validate recipient, expiry, status transition and one-time claim requires the live Directus policy/Flow or a dedicated endpoint; the client check alone does not establish these controls.

**A43 — High: acceptance is a direct, non-atomic invitation update.** `organization_invitation_service.dart:91–125` PATCHes `request_invites/{id}` to claimed with client-supplied `accepted_user` and `claimed_at`. Membership provisioning is assumed to occur elsewhere; this path contains no transactional claim/assignment and no client expiry/status recheck before the write. A stale or concurrent invitation can therefore be marked claimed without this client proving that access was granted. The exploitability of changing another user's invitation depends on server policy and is unverified. Fix: use a protected server claim action that derives recipient from authentication, checks allowed state and server time, and performs claim plus membership creation atomically. Return explicit already-claimed, expired, wrong-account and activation-pending results.

**A44 — Medium: post-acceptance refresh failure can be shown as acceptance failure.** After the PATCH succeeds, `_refreshWorkspaceStateAfterAccept` makes further requests (`organization_invitation_service.dart:116–126,175–245`); errors from them are not caught at the mutation boundary. `OrganizationInvitationScreen` displays any thrown error while leaving Accept available (`organization_invitation_screen.dart:157–176`). A retry can repeat a claim that already committed. The decline path similarly refreshes after a successful PATCH (`organization_invitation_service.dart:146–169`). Fix: record the successful mutation immediately, then show a separate retryable workspace-refresh state; do not repeat the invitation write to refresh UI.

## 4. Push registration and session exit

Startup/resume, verified role routing, workspace switching, workspace creation and FCM token refresh call `PushNotificationService.syncCurrentDevice` (`main.dart:460–468`; `role_based_shells.dart:218–226`; `workspace_access_screen.dart:178–191`; `business_profile_wizard_screen.dart:547–556`; `push_notification_service.dart:410–415`). **A48 — High: logout revokes only the currently active workspace's device row.** `auth_service.dart:455–478` calls `unregisterDevice` before clearing the session. The endpoint resolves only `directus_users.active_business_profile` and `revokeSubscription` filters by user, that business profile and device ID (`backend/directus-extension-endpoint-wellar-push-subscriptions/src/index.ts:134–183,316–340,441–465`). **A49 — Medium: a transient push-initialization failure is latched.** `_initialize` sets `_initialized = true` before permission/local-notification/listener/token setup and catches errors without resetting it (`push_notification_service.dart:154–174`). **A50 — Medium: sync success diagnostics overstate what the response proves.** `ProtectedPushSubscriptionApi.sync` maps any 2xx body with `ok: true` to `subscriptionResult: 'synced'` and `lastSeenUpdated: true` (`protected_push_subscription_api.dart:82–103`). A live database read is still needed to prove deployment behavior.

`PushSyncController` has no production caller (`push_sync_controller.dart:9–54`; repository reference search), while `PushNotificationService` implements the live path. The service does not currently suppress unchanged-token syncs, which allows server `last_seen_at` updates. The source endpoint uses a transaction and advisory lock for the user/business/device key; unique-index and live concurrency behavior still need verification.

**A51 — High: the client completion PATCH includes a field absent from the committed schema snapshot.** `request_service.dart:512–545` sends `wellness_scan` together with `completed_scan`, `completed_at` and status. The `scan_requests` fields in `backend/directus/schema/directus-schema.snapshot.yaml:7587–8087` include `completed_scan` but no `wellness_scan`. **A52 — High, needs integration confirmation: cancellation's lock and write use different database handles.** The cancel endpoint creates `requestsService` with `knex: database` (`backend/directus-extension-endpoint-wellar-scan-request-cancel/src/index.ts:90–94`), then opens `database.transaction`, locks the row with `trx(...).forUpdate()` and calls `requestsService.updateOne/readOne` inside that transaction callback (`:116–207`). The service is not passed `trx` in this source. **A53 — Medium: request lookup converts transport and permission failures into not-found.** `request_service.dart:429–464` returns null for every Dio error after logging it. `ScanRequestOpenScreen` treats null as "Scan request not found" (`scan_request_open_screen.dart:59–69`), so offline, 401, 403 and backend 5xx look like a missing request. **A54 — Medium: a due date selected as today becomes overdue during that day.** `admin_scan_requests_screen.dart:729–738,750–755` stores the date-only value returned by `showDatePicker` and sends it as an instant; `RequestItem.displayStatus` marks it overdue once `dueAt.isBefore(DateTime.now())` (`request_item.dart:157–177`). Fix: present an explicit time picker or send a date-only contract with end-of-day semantics and a clear timezone. Test today, tomorrow and timezone changes.

The older `CreateRequestView` and `RequestsView` components have no production constructor caller found in `lib/`; their email/role/required-state form and one-second request polling are dormant. They should not be counted as the current creation flow without proving reachability.

## 6. Pricing, subscription and feature access

The reachable pricing page is opened from subscription gates and offers a Business plan. Selecting it with an existing profile calls `upsertSubscriptionForProfile`; the management page's Renew and Upgrade actions use the same service (`pricing_screen.dart:234–311`; `subscription_management_screen.dart:356–505`). The service directly PATCHes `business_profiles` billing fields, then POSTs/PATCHes `subscriptions` (`subscription_service.dart:198–235,485–549`). No payment checkout, provider confirmation or server-issued entitlement appears in this mobile path. The committed backend contract notes that `plans` and `subscriptions` are referenced but missing from its sanitized schema (`backend/directus/docs/runtime-contract-cleanup-summary.md:41–51`); deployed collections and permissions are not inferred from that historical export.

**A55 — High: the app presents a paid-plan upgrade after direct client writes, without a payment result.** `pricing_screen.dart:268–307` and `subscription_management_screen.dart:487–508` report an active upgrade after `SubscriptionService.upsertSubscriptionForProfile`; that method calculates expiry locally and writes `billing_status: active` plus `subscriptions.status: active` (`subscription_service.dart:198–235,485–549`). If deployed Directus permissions allow those writes, the client can grant paid access without a verified charge; if they reject them, the current Subscribe/Upgrade flow cannot complete. This is a source-confirmed missing payment/entitlement boundary, not a claim about actual deployed billing. Fix: have a protected backend entitlement action consume verified provider events or a documented admin grant, and let the app display only server-confirmed status. Test paid, failed, pending and refunded outcomes.

**A56 — High: synthetic subscription fallback can grant indefinite Business access.** When no subscription record is returned, `_fallbackSubscriptionFromBusinessProfile` maps a Business `plan_code` with blank `billing_status` to `active`, even if no expiry exists (`subscription_service.dart:575–633`). `canUseBusinessSubscription` accepts active with null expiry (`:305–323`), and `canUseBusinessProvider` drives feature gates (`app_providers.dart:371–384`). A profile with these fields can therefore unlock gated screens without a verified subscription. Fix: use a server entitlement as the only access source; treat missing or inconsistent billing records as unavailable, with a separate recovery path for migration.

**A57 — High: subscription lookup can use a different workspace's latest record.** `fetchActiveSubscription` tries the active business profile, then falls back to the newest subscription for the user regardless of `business_profile` (`subscription_service.dart:125–142,405–434`). `accessForSubscription` checks plan/status/expiry but not whether the returned record matches the active workspace (`:296–327`). A user with multiple workspaces can see an entitlement from one workspace applied to another in client feature gates. Server permissions may still block the underlying data, so this is a client scope defect, not proof of cross-tenant API access. Fix: bind entitlement lookup and access evaluation to the verified active business profile; never use a user-wide record as workspace access.

**A58 — High: profile and subscription billing writes are not atomic.** `upsertSubscriptionForProfile` updates `business_profiles` first, then writes `subscriptions` (`subscription_service.dart:216–235`). Failure or timeout on the second write leaves the profile claiming active/trial billing while the subscription record is absent or stale. The synthetic fallback in A56 can turn that partial state into access. Cancellation reverses the order, PATCHing the subscription before the profile (`:254–275`), with the same partial-state risk. Fix: move both changes into one server transaction driven by a verified entitlement event and return a single committed state.

**A59 — Medium: monthly expiry can skip February for end-of-month starts.** `_computeExpiry` constructs `DateTime.utc(start.year, start.month + 1, start.day, ...)` (`subscription_service.dart:672–696`). Dart normalizes an invalid day in the following month; a January 31 start therefore lands in March rather than at the end of February. Fix: define calendar-month billing semantics with the provider's period end as authority; if local preview is needed, clamp the day to the destination month's last day and test leap years.

**A119 — High: business-center list queries become unscoped when organization resolution fails, and accept arbitrary caller IDs.** `fetchLocations`, `fetchAutomationRules`, and `fetchInvoices` add `filter[org_id][_eq]` only if `_resolveOrgId` returns a nonempty ID (`business_center_service.dart:112–187`). That resolver returns any supplied ID without verifying active-workspace membership, or null when primary organization resolution fails (`:190–197`). In either case the client may issue a broad or wrong-organization query if backend permissions allow it. Fix: require a verified active organization ID, reject a mismatched supplied ID, and fail closed when context is unavailable; keep server tenant checks independent.

**A120 — Medium: admin request routing accepts a global Directus role when the active membership role differs.** `fetchWorkspaceRequests` treats `workspace.directusRoleName` of owner or HR as sufficient even if `finalEffectiveRole` and `memberRole` do not match (`admin_request_service.dart:43–71`). **A121 — Medium: audit-log permission and authentication failures appear as no logs.** `fetchLogs` returns `[]` on 401/403 for each query attempt and after all fallbacks (`audit_log_service.dart:71–101`). ## 27. Manager, HR and member-identity services

`manager_ops_service.dart`, `hr_ops_service.dart`, and `member_identity_service.dart` were read fully. Their direct workforce/scan queries generally carry a business-profile filter, and both operations services compare workspace revisions before returning most assembled snapshots (`manager_ops_service.dart:208–212,322–338`; `hr_ops_service.dart:228–234,604–616`). The gaps below affect scope, completeness and error signaling.

**A122 — High: manager team query becomes department-wide when the manager has no department ID.** `fetchTeam` accepts an active workspace with a business profile even if `departmentId` is null (`manager_ops_service.dart:68–77`), then passes that nullable department into the member query (`:86–97`). `MemberIdentityService` only adds the department filter when the value is nonempty (`member_identity_service.dart:98–115`). A manager with unresolved department therefore requests every active member in the profile, subject to backend permissions. Fix: require a verified manager department before team reads and enforce the same department boundary on the server.

**A123 — Medium: fixed scan and roster windows can mark checked-in staff missing.** Manager and HR workforce enrichment read only the newest 300 scans (`manager_ops_service.dart:107–123`; `hr_ops_service.dart:360–379`), then find each member's latest scan from that subset and derive `missingCheck` from the absence of a scan today (`manager_ops_service.dart:144–203`; `hr_ops_service.dart:381–436`). HR also limits member rows to 200 (`hr_ops_service.dart:344–354`); manager does likewise (`manager_ops_service.dart:86–97`). Busy workspaces can omit members or today's scans beyond those windows, producing false missing-check counts in snapshots (`manager_ops_service.dart:273–278`; `hr_ops_service.dart:535–553`). Fix: query per-member latest completed scan or server aggregates for the selected day, and paginate the roster.

**A124 — Medium: HR and manager snapshot counters are capped and can undercount.** Both snapshots count open alerts from only 100 rows (`manager_ops_service.dart:280–305`; `hr_ops_service.dart:555–575`). Pending requests use `RequestService` defaults of 50 for manager and 100 for HR (`manager_ops_service.dart:311–316`; `hr_ops_service.dart:579–584`; `request_service.dart:198–216,221–224`). HR also counts departments from only 300 rows (`hr_ops_service.dart:588–603`). These are presented as totals. Fix: use backend count/aggregate queries with matching workspace scope, or paginate all relevant rows.

**A125 — Medium: HR overdue compliance silently becomes zero on read failure and is capped at 300.** `fetchCompliance` initializes `overdue = 0`, queries at most 300 scan requests, and ignores any query exception (`hr_ops_service.dart:690–711`). The returned `HrComplianceSummary` exposes zero as a real count (`:725–730`). Fix: preserve an unknown/error state on failure and compute a scoped overdue count on the server or paginate all requests.

**A126 — Medium: member-identity diagnostics print personal identity and backend response bodies.** `resolveFromUserRelation` logs raw expanded user objects, IDs, names and email (`member_identity_service.dart:419–479`); query fallbacks log full response bodies and stack traces (`:168–173,196–210,231–240,615–621,684–691`). These calls are plain `debugPrint`, so source contains no release-mode redaction guard. Fix: remove raw identity/body logging, retain operation IDs/status/error codes only, and gate any diagnostic detail to a controlled debug build.

**A127 — Medium: member-identity fallback turns query failures into an empty roster.** After an authorized identity fallback finds member IDs, a failed `/items/business_profile_members` read catches `DioException` and returns `[]` (`member_identity_service.dart:273–321,322–343`). Callers can render “no members” rather than distinguish permission/network failure. Fix: propagate a typed fallback failure and let the roster UI show a retryable error, while keeping a truly empty successful response distinct.

## 28. Owner operations service

`owner_ops_service.dart` was read fully. Its main workforce, request and alert queries carry an active business-profile filter (`owner_ops_service.dart:417–445,1559–1577,1631–1643`). Workspace revision checks guard several assembled return paths (`:301–306,643–663,729–749`), while the following calculations and fallbacks still cause incorrect or incomplete results.

**A128 — High: owner and HR readiness distributions are capped before date filtering.** `fetchWorkspaceReadinessSummary` requests the newest 800 scan results, then applies `start`/`end` locally to that subset (`owner_ops_service.dart:1231–1259`). A selected older period can show zero or an incomplete distribution even when matching older results exist; this propagates to owner reports, HR compliance and their drilldown. The owner home distribution separately caps at 500 (`:816–840`), so its all-time counts are also incomplete. Fix: send the period bounds to a server-scoped query, page all matching results or use server aggregates, and label any deliberate recent-only view.

**A129 — Medium: owner completion rate can exceed 100% because numerator and denominator use different member sets.** `fetchSnapshot` counts `activeMembers` from active roster rows but counts today's completed and missing checks across every returned member (`owner_ops_service.dart:664–670`). The workforce query's `activeOnly` mode includes `active,pending` for `OwnerWorkforce` (`member_identity_service.dart:105–114`), so a pending member with a check increases the numerator but not the denominator. `fetchReportsSummary` repeats that mismatch (`owner_ops_service.dart:1117–1145`). Fix: choose one eligible member set for both completed/missing counts and the rate denominator, and separately label pending member activity.

**A130 — Medium: owner company summary can return a previous workspace after a switch.** `fetchCompanySummary` captures a workspace revision/signature and checks it before its profile request (`owner_ops_service.dart:535–575`), then awaits the profile, workforce and departments before returning without another stale-result check (`:576–597`). If the active workspace changes during those awaits, the old company's name and counts can be returned to the caller. Fix: validate the captured revision/signature immediately before returning and discard stale results.

**A131 — Medium: owner request counts and overdue flags can silently undercount or become zero.** `_fetchRequestRowsForProfile` applies a fixed 300/400 limit and returns `[]` on every exception (`owner_ops_service.dart:717–719,1555–1580`); `fetchOverdueRequestsCount` also catches failures and returns zero (`:1158–1175`). Workforce overdue badges use that same capped request source (`:444–466`). Fix: use scoped count queries or pagination and carry a typed unavailable state instead of equating failure with zero.

## 29. Scan service completion

`scan_service.dart` was read fully, including history and result lookups, scan and media writes, upload retries, member snapshot fallback and diagnostics. The following service defects are additional to the scan completion issues in A45–A47.

**A132 — Medium: history load treats network and permission failures as an empty scan history.** `fetchHomeData` returns `HomeData(results: [])` on a 403 or a transient network error (`scan_service.dart:350–401`). Its callers receive a successful empty dataset and can show no history even when records exist. Fix: propagate typed permission/offline failures and reserve an empty result for a successful read.

**A133 — Medium: history timeline performs one result lookup per scan in series.** `fetchHistoryTimeline` gets up to `limit` scan rows and then awaits `fetchScanResultLookupForScan` in a loop for every ID (`scan_service.dart:189–253`). The default history limit can make this 200 sequential result requests, increasing load time and the chance of partial data when one lookup fails. Fix: batch result reads by scan IDs, preserve scan order locally, and expose partial-read failures.

**A134 — Medium: the home/history dataset ignores the active workspace.** `fetchHomeData` calls `_fetchUserScanIds` without `businessProfileId` and falls back to `_fetchResultsByUser` without it (`scan_service.dart:350–378`). `_fetchUserScanIds` only adds a workspace filter when one is passed (`:1478–1503`), so this path combines the signed-in user's scans across workspaces despite its use in workspace-specific analytics and exports. Fix: pass the verified active workspace profile to both queries and define a separate explicitly labeled all-workspaces personal history if needed.

**A135 — Medium: scan creation can accept a caller workspace and member ID without a client binding check.** `createWellnessScan` accepts `businessProfileId` and `memberId` supplied by its caller and prefers them while building the write (`scan_service.dart:406–485`); `_loadMemberSnapshot` looks up the member by ID and returns only role/department/shift data, without comparing that member's profile to the selected profile (`:1859–1889`). A stale or mismatched caller context can therefore submit inconsistent scan metadata. Whether the backend rejects the write depends on live access rules. Fix: resolve the active membership, require its profile and user to match the scan target, and enforce the same binding server-side.

**A136 — Medium: video upload retry can repeat a successful non-idempotent file creation.** `uploadVideoFile` retries `POST /files` on a 502 after two and five seconds (`scan_service.dart:937–1040`). A 502 can occur after the server stores the first upload, so a later attempt can create duplicate orphan files while the client retains only the final ID. Actual duplicate creation requires a live backend failure and remains unverified. Fix: use an idempotent upload operation or reconcile uploads by a stable scan/media key before retrying.

## 30. Shared model parsing and status logic

The model files under `lib/models/` were read fully. The parsers generally retain raw backend strings and use defensive date/number conversions; the following inconsistencies are client-side and affect multiple screens.

**A137 — Medium: a sent request is shown as open but cannot be started.** `RequestItem.displayStatus` preserves `sent` as a live status (`request_item.dart:158–172`), while `isActionableCanonical` allows only pending, requested and assigned (`:181–184`). Employee, HR and manager request screens and the shared action card gate scan start on that predicate (`employee_requests_screen.dart:156`; `hr_requests_screen.dart:161`; `manager_scan_requests_screen.dart:152`; `scan_request_action_card.dart:73–91`). A backend request in `sent` state can therefore be displayed without its expected start action. Fix: define one canonical request-state mapping and include `sent` if it represents an outstanding assignment, with backend-contract verification of the intended state transitions.

**A138 — Medium: scan result parsing can display risk level as the overall readiness state.** `ScanResult.fromJson` picks `risk_level` before `overall_state`, then assigns that chosen value to both `riskLevel` and `overallState` (`scan_result.dart:64–81`). If both fields are present and differ, the UI state uses risk level and silently discards the explicit overall state. Fix: parse these fields independently and normalize each according to its own contract; add a fixture with both populated and different values.

The shared widgets under `lib/widgets/` were read fully, including the owner design system, workforce card and bottom-sheet builder. Their hardcoded labels are included in the localization pass below.

**A139 — Medium: an unknown readiness label receives the Stable color.** `ReadinessStatusChip` selects high/elevated/low colors by substring and assigns its green success color to every other value (`owner/owner_design_system.dart:268–286`). ## 32. Providers and shared utilities

`app_providers.dart` and the remaining `lib/utils/` files were read fully, including platform branches, request normalization, scan display and video compression. The following provider and normalization paths can distort cross-screen state.

**A143 — High: a latest-result override can inject a scan from another workspace.** `latestScanResultProvider` holds a single unscoped result (`app_providers.dart:54–55`). `ownerHistoryTimelineProvider` reads a workspace-scoped timeline and then prepends that global result without checking its scan's business profile (`:161–176,188–209`); `homeDataProvider`, `homeScansProvider` and `historyProvider` do the same for their own lists (`:118–154,179–185`). After a workspace switch, a previous workspace's result can appear in the active workspace history until the override is cleared. Fix: key latest results by verified workspace and user, clear on session/context changes, and compare the scan's workspace before merging.

**A144 — Medium: unknown request states are silently treated as Pending.** `RequestStatusNormalizer.normalizeRaw` maps every unrecognized raw status without a completed scan or past due date to `pending` (`request_status_normalizer.dart:72–82`), including a future backend state such as rejected or blocked. It logs the unknown state but returns an ordinary Pending label (`:85–105`). Fix: add an explicit Unknown state, preserve the raw status for diagnostics, and update known state mappings when the backend contract changes.

**A145 — Medium: unread notification and open-alert badges show zero while their sources are loading or failed.** `unreadNotificationsProvider` and `openAlertsCountProvider` return zero from `orElse` for every non-data `AsyncValue` (`app_providers.dart:330–344`). Header badges can therefore imply that there are no unread notifications or open alerts during an authentication, permission or network failure. Fix: expose loading/error state to the badge, or retain a last-known count with a stale indicator; use zero only after a successful empty read.
