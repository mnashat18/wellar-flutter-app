# Wellar AI / Conntinuity — Mobile Reliability Audit

**Scope:** Flutter mobile repository, current checkout, with particular attention to the employee scan journey and a 2,000-employee deployment. **Audit only:** no application/API changes, commits, or releases were made. This report describes code evidence, not production telemetry or a live-system penetration test.

## Executive finding

The scan journey has useful in-process guards and a reasonably explicit media/finalization pipeline, but it is not crash-resumable and cannot establish exactly-once AI processing. Important guards (`_scanId`, active futures, process-requested IDs) live only in widget/service memory. Several shared HTTP retries replay writes, and an uncertain timeout can be presented as “RETAKE NEEDED,” inviting a second paid scan while the first may still be processing. Employee workforce/history data paths also use large fixed limits and one history path is N+1. I would not claim readiness for 2,000 simultaneous employees from this client repository alone; backend capacity, deployed policies, and operational telemetry remain unverified.

## Scan request and result trace

1. `lib/screens/scan_flow_impl_normalized.dart` owns capture and scan orchestration. It captures video/audio, starts media pre-finalization, and `_finishScan` uses `_submitting` plus an in-memory `_scanId` to prevent duplicate submits in the mounted flow. It creates a `wellness_scans` row when the ID is absent, then starts the workflow. `_workflowFuture` coalesces calls only for this widget/process lifetime.
2. `lib/services/scan_service.dart` `createWellnessScan` first queries up to ten recent in-progress scans for the member/profile over ten minutes, then POSTs a new row if none is found. This read-before-create is not atomic, has no client idempotency key, and can race across devices. Conversely, a recent existing scan can be reused for a new capture, conflating attempts.
3. `lib/services/scan_finalize_service.dart` uploads audio, awaits any early video/thumbnail uploads (or falls back to upload), creates `scan_media`, marks the scan `media_ready`, then POSTs `/process` through `ScanService.triggerAiServerProcess`. The finalizer coalesces by scan ID only while its future is active. `_aiProcessRequestedScanIds` is a process-local set and is populated only after a 202 response.
4. `lib/screens/scan_flow_impl_normalized.dart` polls scan status and result visibility. `lib/screens/scan_details_screen.dart` has its own result/status poller. `lib/services/scan_sync_service.dart` also contains a longer polling/history recovery path. These overlapping strategies are not one shared persisted state machine.
5. Result retrieval uses `/items/scan_results` filtered by scan ID. A completed status without a visible result triggers additional lookups; a timeout can become a retake action rather than reconnecting to the same scan.

## Findings and evidence

| Priority | Finding | Evidence / impact |
|---|---|---|
| P0 | AI dispatch is not demonstrably idempotent end-to-end. | `lib/services/scan_finalize_service.dart` process-local `_aiProcessRequestedScanIds`; `lib/services/scan_service.dart` `triggerAiServerProcess` POSTs `/process` with `scan_id`, without an idempotency header or durable dispatch record. A timeout/5xx may occur after server acceptance. Client code cannot prove whether retrying is safe without server behavior. |
| P0 | Ambiguous completion can lead to a second scan / repeated AI cost. | `lib/screens/scan_flow_impl_normalized.dart` `_retryFinalizeAfterFailure` clears `_scanId` and finalization state; `lib/screens/scan_details_screen.dart` timeout UI labels the outcome “RETAKE NEEDED” and offers a fresh flow. If the job is still running or dispatch response was lost, that can create a new scan. |
| P0 | Shared retry middleware may replay non-idempotent writes. | `lib/services/directus_client.dart` transient/fallback retry logic applies to requests without restricting retries to safe methods; affected operations include scan creation, media creation, and `/files` uploads. `lib/services/scan_service.dart` also retries video upload on 502. A lost response does not establish that the server rejected the write. |
| P1 | No durable recovery after process death or force-stop. | Scan ID, workflow future, media staging futures, and process-dispatch set are in widget/service memory (`scan_flow_impl_normalized.dart`, `scan_finalize_service.dart`). `dispose` cancels timers/resources but does not persist a job checkpoint. Reopening cannot reliably reconnect to an outstanding job. |
| P1 | Timeout/retry behavior is inconsistent across layers. | `lib/services/directus_client.dart` defaults to 15s connect/20s receive and generic retries. Video upload in `lib/services/scan_service.dart` has much longer per-upload limits; audio uses shared defaults; AI processing uses a separate Dio with 15s connect/30s receive and does not participate in Directus token refresh. This can produce ambiguous timeouts and divergent error handling. |
| P1 | Pollers are duplicated and produce avoidable request load. | `scan_flow_impl_normalized.dart`, `scan_details_screen.dart`, and `scan_sync_service.dart` each implement polling. Scan details polls status every 2s initially, then every 4s, with a result consistency window; sync service can poll for up to 120s and perform repeated home-history reads. `lib/utils/scan_result_polling_policy.dart` exists but is not the scan-details polling policy. |
| P1 | Employee-scale listing is fixed-limit and not proven for 2,000 staff. | `lib/services/member_identity_service.dart` directory default is 500; owner/HR/manager operations use caps (including 200–800 scan/member rows). `lib/screens/owner_workforce_screen.dart`, `hr_workforce_screen.dart`, `manager_team_screen.dart` render mapped collections rather than paging/lazy `ListView.builder` paths. Limits can omit employees; large in-memory lists/builds affect low-end devices. |
| P1 | History retrieval includes an N+1 path. | `lib/services/scan_service.dart` `fetchHistoryTimeline` retrieves per-scan results sequentially (up to 200 scans); a 200-entry timeline can require roughly 1 + 200 requests. Home providers also independently call `fetchHomeData(limit:50)` for home data and home scans (`lib/state/app_providers.dart`). |
| P1 | Video memory/storage cost is weakly bounded on device. | `lib/screens/scan_flow_impl_normalized.dart` selects `ResolutionPreset.veryHigh` despite a 1280×720 target comment. `lib/utils/video_compress_io.dart` sets a quality profile and frame rate; the logged target bitrate is not passed as a compressor option. Compression may return original input on failure. Raw/temp compressed copies use `deleteOrigin:false`; upload/retake cleanup is not evident. Mobile multipart-from-file avoids whole-file buffering, but the web branch reads bytes. |
| P1 | Privacy-sensitive debug logging is not consistently redacted. | `lib/utils/video_compress_io.dart` logs complete local video paths and errors. `lib/services/member_identity_service.dart` logs profile/member identifiers and relation data in some debug paths. Scan-flow logs include scan/workspace/membership IDs and roles. `safe_debug_log.dart` exists, but direct `debugPrint` callers bypass its allow-list. Logs may persist in device/system diagnostics. |
| P1 | Crash reporting is not configured in the app. | `lib/main.dart` installs Flutter and platform error hooks that log locally; platform handler returns `false`. `pubspec.yaml` includes Firebase core/auth/messaging but no Crashlytics/Sentry package. No central crash/performance reporting is evidenced. |
| P2 | Periodic UI work and lifecycle handling can waste resources. | `scan_flow_impl_normalized.dart` rebuilds status UI via a 700ms periodic `setState`; it does cancel timers on dispose and removes the observer. Lifecycle handling primarily protects capture preview and does not checkpoint/reconcile processing state. Details polling has no equivalent explicit lifecycle pause/resume policy. |
| P2 | Token renewal is split by API client. | `lib/services/directus_client.dart` performs single-flight refresh and retries an authorized request once after 401. `triggerAiServerProcess` creates a separate raw Dio and uses the current bearer token without this refresh path. Tokens are stored through `FlutterSecureStorage` in `lib/state/session.dart`, which is a positive baseline; actual device backup/access-control configuration still needs platform verification. |

## Asynchronous state and reconnection proposal

Keep the current deployed endpoint and payload contract in the first mobile-only increment. Represent one scan as a durable local job keyed by the server `scan_id`, with explicit states:

`capturing → uploading_media → media_ready → dispatching/dispatch_uncertain → processing → result_available`

Terminal or recoverable branches: `failed_retryable`, `failed_terminal`, `offline_waiting`, `needs_auth`, and `needs_user_action`. Persist only the minimum recovery metadata (scan ID, media IDs, current stage, last transition/time, dispatch state, workspace/member binding) in a local job store. Do not persist raw media in an unprotected location longer than necessary.

On launch/resume, reconcile the stored scan against the existing scan status endpoint first. If processing/completed, continue status/result retrieval; if completed but result is temporarily absent, retry result reads only. If dispatch is uncertain, reconcile status before any `/process` retry. If media is ready and server still reports a state that safely permits dispatch, invoke the existing process endpoint once from the client. Never turn “still running / status unavailable” into a new scan automatically. A “Resume/check status” action should be distinct from “Start a new scan.”

The client alone cannot promise exactly-once processing if the deployed `/process` handler is not idempotent. Preserve current API compatibility now and obtain backend confirmation that `scan_id` deduplicates dispatch. If it does not, a future coordinated server change is required; do not silently introduce a new header or endpoint without server support.

## Scale, verification boundaries, and regression focus

This is a repository audit, not a load test. “2,000 employees” may mean tenant size, not 2,000 concurrent scans; concurrency targets and scan frequency must be defined. The codebase does not provide server queue capacity, AI throughput, Directus rate limits, result SLOs, deployed Directus policy state, or field-device performance data. Checked-in Directus permission snapshots are intended configuration only and do not prove deployed settings.

Before rollout, test delayed/lost responses after each write, double taps, parallel devices, app kill/background/resume, expired access token, offline transition, completed-with-late-result, low storage, compression failure, and 401 during `/process`. Add metrics for scan stage duration, upload bytes/retries, dispatch outcomes including uncertain, poll requests, result latency, resumed jobs, duplicate scan IDs, and terminal reasons. Never attach media, tokens, emails, or raw response bodies to telemetry.
